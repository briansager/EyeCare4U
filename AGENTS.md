# EyeCare4U contributor guidance

- Work only in the requested milestone. Do not begin the next milestone without a user request.
- Standing owner authorization: after each milestone, run the required validation, review all changes and staged contents for accidental or unrelated files and secrets, then commit and push to `origin/main` when the required automated checks pass. Routine milestone commits and pushes do not require another confirmation. This authorization replaces the earlier instruction to stop before committing or pushing.
- Exclude generated output, local settings, secrets, databases, and unrelated files from commits. Preserve user changes and documented outstanding manual checks. Automated checks do not verify tray behavior, actual Windows text/display scaling, or screen-reader behavior.
- Inspect origin and remote history before publishing. Never force-push, overwrite remote history, or discard user changes. If authentication or remote divergence blocks publication, report the precise blocker.
- After pushing, check the resulting GitHub Actions run when tooling permits. Fix implementation-caused CI failures, rerun validation, commit, and push the correction under the same authorization. Report the commit hash, push result, CI status, and remaining manual checks.
- `EyeCare4U.slnx` contains `src/EyeCare4U.App` (WPF views and view models), `src/EyeCare4U.Core` (UI-independent logic), and `src/EyeCare4U.Storage` (serialized SQLite persistence).
- Follow straightforward MVVM. Keep view code-behind limited to UI concerns. Core must not reference WPF or the App project. Avoid speculative services and containers.
- Use the SDK policy in `global.json` and README for local development and CI. Validate with `dotnet restore EyeCare4U.slnx` and `dotnet build EyeCare4U.slnx --configuration Release --no-restore`.
- Launch with `dotnet run --project src/EyeCare4U.App/EyeCare4U.App.csproj --configuration Release --no-build`. Check resizing, keyboard scrolling, and increased display/text scaling after UI changes.
- `tests/EyeCare4U.Core.Tests` covers timer/input behavior; `tests/EyeCare4U.App.Tests` covers view-model commands and validation. `tests/EyeCare4U.Storage.Tests` covers temporary SQLite databases, recovery, and clear/write ordering. Run `dotnet test EyeCare4U.slnx --configuration Release --no-build --no-restore` after the Release build. Tests must advance injected time without real waits. Do not add empty test projects or tests of constants merely to report success.
- Keep Ready/Running/Paused/Due transitions in Core. Use monotonic timestamps, not UI tick counts. Window and tray must share one timer; interval changes are allowed only in Ready. Milestone 5 persists validated preferences and accepted history under LocalApplicationData/EyeCare4U; never persist a live countdown or fabricate closed-app activity. ActivitySession now supplies the application reminder with a credited-activity clock. Usage remains independent of reminder state. Failures, lifecycle boundaries, and gaps over five seconds exclude unresolved time and require fresh baselines. Idle threshold changes are prospective, saved at checkpoints, and allowed only in Ready. Keep native input/session/power calls inside the Windows adapter; use injected time and simulated signals in tests. ReminderExperience coordinates the app commands: break uses a separate monotonic 20-second timer, snooze uses credited activity, and normal/snooze/break consumption must never overlap. Break interruption precedes completion on unreliable samples or lifecycle changes. Due alerts get one eligible attempt per occurrence; Reset/shutdown invalidate pending effects. Never activate a window except after explicit user Open/notification click. No claims of verified eye rest or fullscreen compatibility.
- Describe future usage measurements as estimates. Input inactivity does not prove absence, looking away, or attention. Do not imply medical treatment or an optimal break schedule.
- Prefer local processing and minimal data collection. Clearly distinguish privacy intentions from implemented behavior; never imply unimplemented privacy controls exist.
- Computer vision is deferred exclusively to Milestone 7. Do not add camera access, AI dependencies, presence/gaze estimation, or placeholder AI services earlier.
- Do not add a license before the owner chooses one.

- History consumes exact accepted ActivitySession windows. Keep UTC plus recorded date/offset/zone, monotonic durations, stable IDs, epoch-protected clear boundaries, and off-UI FIFO database operations. Preserve corrupt/newer data on failure. Default launch is always Ready; saved preferences apply before the first monitoring baseline. Clear keeps preferences, current timer and session estimate. Do not commit actual databases or user history.

- Milestone 6 candidate version lives in Directory.Build.props. Keep packages.lock.json files current deliberately; package with scripts/Package-Portable.ps1 (locked restore, full build/tests/audit before self-contained publish). Generated ZIPs/manifests/smoke data belong under ignored artifacts/ only. No installer, signing, Release/tag or autostart is authorized by the candidate workflow.
- Use scripts/Start-IsolatedReview.ps1 and temporary databases for destructive qualification. Never delete real owner history to complete a test. Preserve the single Windows matrix and public-release blockers in docs/MILESTONE-6-REVIEW.md; unit tests do not prove OS integration. Preserve upstream third-party notices byte-for-byte; they do not select the project's license.
